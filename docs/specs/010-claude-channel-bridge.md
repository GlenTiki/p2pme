# Claude native channel bridge

The bridge connects an approved browser grant to an existing Claude conversation through Claude's native MCP channel. Managed `start claude` sessions remain a separate option. Setup does not launch Claude, submit an initial prompt, or edit existing user settings. Approved remote requests subsequently enter the selected conversation under its existing tool permissions. A grant can ask that session to read files and return their contents; pairing consent must state that authority.

## Local setup

`p2pme claude-setup SESSION_ID --output-dir ABSOLUTE_PATH` creates a new private directory with an MCP configuration and a settings file. The files contain a random registration ID, an explicit provider session ID, the local socket path and executable arguments. They contain no invitation or device secret. The command prints an argument-safe native resume command using `--resume`, `--mcp-config`, `--settings` and `--dangerously-load-development-channels server:p2pme`. The user exits the selected Claude process, runs this command to resume the same ID, and accepts Claude's native channel consent. The guide must not start a second process on an active conversation. Existing output directories are rejected. The generated settings contain only SessionStart and SessionEnd hooks, without permission, environment or other settings. The directory is created atomically with mode 0700 and files use mode 0600.

`p2pme claude-channel` runs the stdio MCP server as Claude's child. It connects to the private daemon socket with the generated registration and provider IDs. `p2pme claude-hook` reads bounded hook JSON from stdin and sends only the event name, registration ID and provider session ID to that socket. It never reads a transcript. The daemon socket uses mode 0600 inside its mode-0700 state directory. This OS filesystem boundary excludes other local users. The bridge adds no portable peer-credential API unavailable in Node. Same-user processes already have local daemon authority; the registration ID correlates events rather than authenticating a peer. Its presence in argv adds no authority. Local callers are not proof of human authorship. These operations cannot pair a device or change its grants.

## Conversation boundary

The daemon accepts one channel connection per random registration ID. Both child connection and hook report the canonical working directory. A directory mismatch invalidates the registration against the daemon's approved workspace. It waits for both the connection and a matching SessionStart event before it attaches the adapter to the host. Either can arrive first. Compaction for the same identity keeps that registration. A SessionEnd event, a different SessionStart identity, or a channel socket close permanently invalidates that registration for the daemon epoch. Later replay cannot reactivate it. A new setup has a new registration ID. The registry accepts IDs on their first local hook or child connection and binds each to one provider ID. It keeps at most 64 IDs per daemon epoch, including tombstones, and reports capacity exhaustion. Inactive registrations expire after five minutes into tombstones. IDs are not reused; restarting the daemon resets capacity and requires a new native setup. Before activation the channel is absent from online sessions. Different-session resume, fork or clear requires a new setup.

Claude hooks are a lifecycle signal, not a native session lock. SessionEnd cannot prevent a conversation switch, and its process can fail or time out. A missed hook can leave a stale channel until socket closure. The bridge cannot claim an unconditional conversation-boundary guarantee. Managed Claude processes provide a fixed provider identity when that limit is unacceptable.

## Commands and replies

The daemon exposes the bridge through its private extension seam. The first frame uses the normal local request envelope. A channel client waits for acknowledgement before it sends more frames. Later frames are bounded JSON objects with the registration generation and request ID. Each direction permits one active request and returns busy immediately for another. Unknown IPC frames, malformed values, IPC correlation errors and size violations close the channel. Invalid or late model tool calls return MCP tool errors and never reach IPC. Each subsequent IPC frame has a 64 KiB limit. Initial control frames and hook input have a 32 KiB limit. Input text has an 8 KiB UTF-8 limit; its worst-case JSON expansion fits inside the 64 KiB IPC frame; reply text has a 24 KiB JSON-encoded limit.

The host validates grants and records accepted commands before it calls the adapter. The adapter forwards only the validated text, request kind and principal. The MCP server emits a native channel notification with fixed identifier metadata, the host-assigned principal enum (`human-device` or `agent`) and request kind (`chat`, `task`, or `ui-action`). It escapes ampersands and angle brackets in remote text before the native wrapper receives it. This preserves the wrapper syntax but cannot make a model immune to prompt injection. Claude uses `p2pme_reply` with the request ID and generation. Only that correlated text returns to the host. The host records the result through its normal output callback. Tool output, reasoning, approval requests and transcript history never enter this path. No permission relay capability is declared. The host supplies the structural request kind (`chat`, `task`, or `ui-action`). Text that resembles a UI action remains ordinary chat; labels guide the model but do not create an authorization boundary inside a text-only provider API.

A request expires after five minutes without a reply. Timeout or abort abandons the pending request without interrupting Claude's shared conversation. Claude may still act on a delivered notification and use its existing tools. The error states that limit. Late replies produce tool errors and are never recorded. Detach, hook invalidation and socket failure reject pending work and mark the host session offline. Identity-checked detach cannot remove a newer adapter for the same provider session. Persistent host metadata retains the stable session ID. The daemon never replays saved commands into a channel after restart. An interrupted command can remain without a result in the audit log; it is never marked successful. Output callback failure rejects the request and closes the channel. Tests target Claude Code 2.1.296. The native API gives no capability-delivery acknowledgement: a disabled or unsupported channel can drop notifications silently. The reply deadline detects missing responses; no immediate capability-detection guarantee is claimed.

## Acceptance

Tests use real local Unix sockets and the MCP SDK's in-memory transport without a model. They cover both lifecycle arrival orders, matching reply delivery, wrong generation, wrong session, duplicate registration, abort, socket closure, invalidation replay, output callback failure, bounded frames and private setup files. Generated setup commands include the required hooks and explicit resume identity. Local quality gates pass before commit. A fresh Claude review receives only intended-public p2pme files.

## Review record

The first Claude specification review requested clearer trust, lifecycle and timeout behavior. This revision specifies the existing OS socket boundary, local ID creation, bounded registry, reply deadline, grant authority, safe wrapper text, settings scope and native delivery limits. It rejects the suggestion to add a nonportable peer-credential API: mode-0700 directory access and mode-0600 socket access already enforce the configured same-user trust boundary. Claude `claude-sonnet-5-5` accepted the revised trust and lifecycle contract and requested one remaining correction: input JSON expansion must fit the frame budget. Subsequent IPC frames now permit 64 KiB, which contains the worst-case sixfold expansion of an 8 KiB input plus bounded metadata. The reviewer explicitly accepted the specification conditional on this correction. Real native resume identity remains a manual smoke check; automated tests do not run model inference. Claude `claude-sonnet-5-5` returned SHIP for code bundle `b174d27157104ca979cbcc295bf530eba20de913b59abd32a11c4afa29eb01a7`, with the daemon and host seams treated as external contracts. It suggested three correctness fixes: a completion and next request in one socket chunk, attachment failure cleanup, and split UTF-8 hook input. Reproducing tests failed before each fix. The implementation now waits for a delivered request to settle before the next submission, retires failed attachments, and decodes hook input incrementally. Claude `claude-sonnet-5-5` returned SHIP for corrected bundle `50f62dc67f2440760afe3cc6ed89ea1897dc942bd329ccf99e13b45469fc6eb0`. The review inspected the exact diff and final source but did not independently verify the bundle hash. Local strict types, lint and complexity, formatting, 103 tests and SDK build passed. A cancellation that arrives with a queued next request can still race with delivery; cancellation never promises to prevent Claude from acting. Actual provider inference, native consent and daemon integration remain separate verification steps.
